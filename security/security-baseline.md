# Security baseline

Apply this matrix to every website and record evidence in the release record. N/A needs an architecture-based reason. Use [the implementation guide](../docs/17-security.md), [threat model](threat-model-template.md) and [audit checklist](security-audit-checklist.md).

| Control | Applicability / implementation | Verification |
| --- | --- | --- |
| HTTPS and validated TLS | All deployed sites; managed cert, correct host, intentional HTTP redirect | Actual hostname/browser and certificate validation |
| HSTS | Stable HTTPS domains; start short, review all hosts before includeSubDomains/preload | Actual response and domain inventory; never preload blindly |
| CSP and framing | HTML; restrict sources to actual requirements, tested hashes/nonces for inline code, frame-ancestors | Report-Only preview, console and enforced policy; test widgets/Auth |
| nosniff, referrer and feature policy | Set correct MIME; deliberate Referrer-Policy and Permissions-Policy | GET responses for HTML/assets/API/errors; browser behavior |
| Secure sessions | Auth only; secure cookie/token integration, expiry/revocation, no public caching | Login/logout/refresh/recovery/expired/revoked identities |
| Authentication and authorization | Protected routes/data; server identity and per-action/object checks | Anonymous, user A/B, editor/admin direct API tests |
| CORS | Only cross-origin APIs that need it; exact allowlist, no credential wildcard | Allowed/denied Origin and preflight; CORS is not auth |
| CSRF | Cookie/ambient-credential writes; framework token plus trusted origin/SameSite as appropriate | Cross-site unsafe-method attempts denied; no state-changing GET |
| Input/output | All untrusted input; schemas, bounds, field allowlists, contextual escaping/sanitization | Invalid/oversized/hostile data tests; no raw unsafe HTML |
| SQL injection | SQL only; bound parameters, least privilege and constraints | Query review and malicious input tests in isolated environment |
| Abuse controls | Public writes/auth/costly actions; shared rate controls, bounded work, Turnstile where warranted | Threshold/failure tests; server token verification, expected host/action |
| File uploads | Only if selected; allowlisted signatures/types, byte limits, generated names, private/quarantined originals | Spoofed/oversized/active files denied; access policies tested |
| Secrets and accounts | All; least privilege, MFA, isolated envs, provider secret fields, no committed credentials | Staged/history/client artifact/log review; revocation plan |
| Dependencies and CI | All tooling; lockfiles, alerts, reviewed updates, pinned Actions, minimal permissions | Relevant vulnerability report and workflow review |
| Logs and audit | Dynamic/admin operations; redacted IDs/outcomes, restricted retention | Confirm no password/token/session/body leakage; access review |
| Recovery and incident plan | Source always; DB/files where selected; encrypted backups and isolated restore | Recovery evidence, owner and RPO/RTO; incident exercise |

## Header deployment notes

The [static `_headers` template](../templates/security/_headers) is a starting point for a script-free/static site. It is intentionally not a universal CSP. Add needed script/style hashes/nonces and approved external origins from real runtime requirements. Never broadly add unsafe-inline/unsafe-eval or `*` just to silence console errors. Turnstile, payments and embeds need documented source directives.

Static asset rules do not apply to responses generated by Workers/SSR/API handlers. Set equivalent headers on runtime, denial and error responses; private data also needs `Cache-Control: no-store` and exclusion from application/service-worker caches. Cookie HttpOnly behavior must fit the selected provider's documented SSR architecture rather than breaking a browser SDK.

## Evidence and limits

A scanner finding or a present header is not proof of safety. Pair configuration inspection with actual deployed behavior. Production tests are read-only unless explicitly authorized. Never disable TLS validation, RLS or permission checks to obtain a green test. Review current [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) and [cheat sheets](https://cheatsheetseries.owasp.org/), plus provider security advisories before implementation. Guidance reviewed 2026-10-28; specific site security remains unverified until tested.
